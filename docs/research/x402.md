# x402

**Answer:** Target **x402 v2** (`x402Version: 2`; spec v2.0 dated 2025-12-09, still current). Headers are `PAYMENT-REQUIRED` / `PAYMENT-SIGNATURE` / `PAYMENT-RESPONSE`, all base64 JSON. Networks use CAIP-2, so Hedera testnet is **`hedera:testnet`**. An official `exact` Hedera scheme and `@x402/hedera` already exist, and they match Kosha's design (client-signed `TransferTransaction`, facilitator is the fee payer through `extra.feePayer`, `payload.transaction` base64). One conflict: the official scheme only allows credits to `payTo`, so Kosha's TDS-to-escrow transfer is a Kosha-only extension.

## Snippet
**402 response.** The canonical location is the `PAYMENT-REQUIRED` header, holding base64 (standard alphabet, UTF-8) of this JSON. The v2 body is up to the implementer, so Gate may also send the same JSON as the body.
```json
{ "x402Version": 2,
  "error": "PAYMENT-SIGNATURE header is required",
  "resource": { "url": "https://api.demo-in.dev/v1/gst-lookup", "description": "GSTIN lookup", "mimeType": "application/json" },
  "accepts": [{
    "scheme": "exact", "network": "hedera:testnet", "amount": "100000",
    "asset": "0.0.429274", "payTo": "0.0.5001", "maxTimeoutSeconds": 120,
    "extra": {
      "feePayer": "0.0.4000",
      "kosha": {
        "quoteId": "q_7f3a", "memo": "kosha:q_7f3a", "nodeAccountIds": ["0.0.3"], "expiresAt": "2026-11-06T10:32:00Z",
        "transfers": [ { "account": "0.0.5001", "amount": "100000" }, { "account": "0.0.4100", "amount": "1019" } ],
        "tax": { "rulepack": "in-2026.1", "rateBps": 100, "inrValuePaise": "884", "tdsMicroUsdc": "1019",
                 "funding": "payer", "reason": "threshold_crossed", "flags": [] } } } }],
  "extensions": {} }
```
**Payment payload.** Sent in the `PAYMENT-SIGNATURE` header as base64 JSON. `accepted` is the chosen `accepts[]` entry, echoed verbatim.
```json
{ "x402Version": 2,
  "resource": { "url": "https://api.demo-in.dev/v1/gst-lookup" },
  "accepted": { "scheme": "exact", "network": "hedera:testnet", "amount": "100000", "asset": "0.0.429274",
                "payTo": "0.0.5001", "maxTimeoutSeconds": 120, "extra": { "feePayer": "0.0.4000", "kosha": { "...": "as above" } } },
  "payload": { "transaction": "<base64 of the frozen, payer-signed TransferTransaction bytes>" } }
```
**Settlement response.** Sent in the `PAYMENT-RESPONSE` header as base64 JSON, on the 200, and also on a 402 when settlement fails (`success: false`, `errorReason`, `transaction: ""`).
```json
{ "success": true, "transaction": "0.0.4000@1762424400.123456789", "network": "hedera:testnet",
  "payer": "0.0.6001", "amount": "100000",
  "extensions": { "kosha": { "hashscanUrl": "https://hashscan.io/testnet/transaction/…", "hcsSequence": 42, "tdsMicroUsdc": "1019" } } }
```
**Facilitator API (v2 §7).**
- `POST /verify` and `POST /settle` take the same body: `{ "x402Version": 2, "paymentPayload": PaymentPayload, "paymentRequirements": PaymentRequirements }`.
- `/verify` returns `{ isValid, invalidReason?, invalidMessage?, payer?, extensions?, extra? }`. It must be read-only.
- `/settle` returns the SettlementResponse: `{ success, errorReason?, errorMessage?, payer?, transaction, network, amount?, extensions? }`.
- `GET /supported` returns `{ kinds: [{ x402Version, scheme, network, extra: { feePayer } }], extensions: [], signers: { "hedera:*": ["0.0.4000"] } }`.

## What this changes in the spec
- `x402Version: 1` becomes `2`. `network: "hedera-testnet"` becomes `"hedera:testnet"`. `maxAmountRequired` becomes `amount`.
- `accepts[].resource` (a string) moves to the top-level `resource: { url, description?, mimeType? }`. `description` and `mimeType` leave the requirement entry.
- Header renames: `X-PAYMENT` becomes `PAYMENT-SIGNATURE`. `X-PAYMENT-RESPONSE` becomes `PAYMENT-RESPONSE`. The 402 now sets the `PAYMENT-REQUIRED` header, because `@x402/fetch` v2 reads only that header and ignores the body.
- `feePayer` moves out of `extra.kosha` to the standard `extra.feePayer`, matching `@x402/hedera`. Don't duplicate it.
- The payment payload becomes `{ x402Version, resource?, accepted, payload: { transaction } }`. Kosha reads `quoteId` from `accepted.extra.kosha.quoteId`, which also appears in the signed memo, so it needs no `payload.quoteId`.
- `amount` means the net credit to `payTo`, which is the API price (`100000`), as the official `exact` rules define it. The payer's total debit is `sum(extra.kosha.transfers)`.
  - **Deviation:** the official Hedera verifier rejects any other credit (`invalid_exact_hedera_payload_extra_positive_transfers`), so only Kosha Core can settle a quote that includes TDS.
  - When TDS is 0, the quote is a fully standard `exact` payment. A generic `@x402/hedera` client could pay it, but it won't set Kosha's memo, so Core would need to fall back to `quoteId` binding. (My inference, untested.)
- Core keeps its `/v1/verify` and `/v1/settle` paths but uses the v2 request and response shapes. Kosha-only verify fields go in `extra` and settle fields in `extensions.kosha`; this placement is a Kosha convention, unconfirmed against any spec. Gate's 402 `error` uses Kosha codes. The facilitator `invalidReason` and `errorReason` use x402 codes where one fits.
- Reusable codes:
  - Standard: `insufficient_funds`, `invalid_payload`, `invalid_payment_requirements`, `invalid_scheme`, `unsupported_scheme`, `invalid_network`, `invalid_x402_version`, `invalid_transaction_state`, `unexpected_verify_error`, `unexpected_settle_error`, and `settlement_pending` (non-terminal; `transaction` must be set).
  - From the Hedera reference code: `invalid_exact_hedera_payload_{transaction_could_not_be_decoded, fee_payer_mismatch, contains_non_transfer_ops, hbar_sum_non_zero, asset_sum_non_zero, asset_mismatch, amount_mismatch, extra_positive_transfers, fee_payer_transferring_funds, signature_invalid, missing_fee_payer}`, plus `network_mismatch`, `invalid_amount`, `fee_payer_not_managed_by_facilitator` and `accepted_payment_requirements_mismatch`.
- CORS (browser Console or Pay): expose `PAYMENT-REQUIRED, PAYMENT-RESPONSE, X-KOSHA-TAX`; allow `PAYMENT-SIGNATURE, X-KOSHA-AGENT, Content-Type`.
- `maxTimeoutSeconds` must stay at or below Hedera's 180 s transaction valid duration.
- **Unconfirmed:**
  - The Hedera scheme doc's SettlementResponse example uses `transactionId` and gives `payer` as the fee payer. The reference code uses `transaction` and gives `payer` as the sender. Follow the code and the core spec.
  - I did not check whether v1 still gets new features.

Recommended `packages/shared/src/headers.ts`:
```ts
export const X402_VERSION = 2 as const;
export const SCHEME_EXACT = 'exact';
export const NETWORK_HEDERA_TESTNET = 'hedera:testnet';
export const HEADERS = {
  paymentRequired: 'PAYMENT-REQUIRED',   // server → client, base64 PaymentRequired
  paymentSignature: 'PAYMENT-SIGNATURE', // client → server, base64 PaymentPayload
  paymentResponse: 'PAYMENT-RESPONSE',   // server → client, base64 SettlementResponse
  legacyPayment: 'X-PAYMENT',            // v1, read-only fallback (optional)
  legacyPaymentResponse: 'X-PAYMENT-RESPONSE',
  koshaAgent: 'X-KOSHA-AGENT',           // Kosha custom, HCS-14 agent id
  koshaTax: 'X-KOSHA-TAX',               // Kosha custom, rate + amount withheld
} as const;
```
